# 新增关卡与指令

修改前先运行 `npm test`，确认已有语义保持稳定。新增内容应仍通过 `Interpreter` 校验参考解与学生程序，避免在地图组件或播放器里添加特殊通关路线。

## 新增一个关卡

在 `src/data/levels.ts` 的 `levels` 数组加入一个 `Level`，并使用新的稳定 ID。不要复用旧 ID 来表示完全不同的地图，否则旧草稿及完成记录会继续关联到这个 ID。

关卡至少填写：章节、序号、标题、故事、学习目标、网格尺寸、起点坐标与朝向、一个终点、障碍、带唯一 ID 的星星、可用指令、三级提示、参考程序与 `mode: 'challenge'`。如需限制积木数，增加 `maxBlocks`；它统计主程序、循环容器、循环内部与 A/B 定义区的存储节点总数，不按调用或重复次数展开。

下面是可以加入数组的完整示例；它仅示范课程扩展，不属于目前交付的 12 关：

```ts
{
  id: '013', number: 13, title: '送星星回家',
  chapter: '05 · 自己规划', mode: 'challenge',
  story: '把两颗星星收起来，沿着拐角小路送到旗子旁。',
  objective: '先预测最终位置，再组合步数和左转。',
  width: 5, height: 5,
  start: { x: 1, y: 3, direction: 'E' },
  goal: { x: 3, y: 2 },
  obstacles: [{ x: 0, y: 0 }],
  stars: [
    { id: '013-star-1', x: 2, y: 3 },
    { id: '013-star-2', x: 3, y: 2 },
  ],
  allowed: ['forward', 'left', 'right'],
  maxBlocks: 3,
  hints: [
    '先看看布布现在面朝哪里。',
    '先沿着起点所在的行走，再向上转弯。',
    '前进2格、左转、前进1格。',
  ],
  solution: {
    main: [
      { id: '013-reference-1', type: 'forward', steps: 2 },
      { id: '013-reference-2', type: 'left' },
      { id: '013-reference-3', type: 'forward', steps: 1 },
    ],
    functions: { A: [], B: [] },
  },
}
```

坐标必须是网格内整数；左上角 `(0, 0)`，北朝向使 `y` 减少。尺寸保持在 4 × 4 至 12 × 12。起点、终点、星星不能在障碍上；障碍坐标与星星 ID 不重复。终点允许与起点相同，例如需要走一圈回来；星星放在起点时不会自动收集，必须离开后再次进入，因此通常避免这样设计。

参考解可以直接写结构化程序，也可以使用同文件的 `program()`/`blocks()` 辅助函数创建稳定且唯一的参考节点 ID。不要把重复使用的同一个节点对象直接放入多个位置：相同语义的积木也必须使用不同 ID。编辑器新建和复制积木由 `createInstruction()`/`cloneInstruction()` 自动分配 ID。

新增后的检查顺序：

1. 运行 `npm test -- src/tests/levels.test.ts`。该文件遍历所有关卡，检查地图合法性、指令限制及参考解真实执行结果。更新其中“当前有 12 个挑战”的数量断言，使其反映课程实际数量；保留分阶段指令检查。
2. 检查顶部总关卡数和下一关逻辑，避免课程数量文案仍写死为 12；关卡选择器从 `levels` 数据生成。
3. 在浏览器选择新关卡。初始草稿应该为空，不能自动装入参考解。按提示逐步编程，再在看完三级提示后试运行参考解。
4. 导出新关卡程序、刷新并重新导入，确认 `levelId` 匹配以及独立草稿保存。另一个关卡的文件应被拒绝。
5. 运行 `npm run typecheck`、`npm test`、`npm run build`，并执行项目已有浏览器测试。

修改已有课程的星星、障碍或允许指令后，仍需重新验证它的参考解与草稿兼容性。完全不同的课程优先分配新 ID；如果必须改变旧数据格式，需要明确实现存档迁移并增加测试，目前加载器不猜测旧版本含义。

## 新增一个指令

新增指令是一项共享语义变更。必须同时修改数据模型、校验、解释器、编辑器和测试。只加一个图标或可点击积木不会产生执行能力。

1. **定义原子语义。** 先决定它算几个原子动作、能否修改坐标/朝向、是否可能碰撞、如何消耗预算，以及暂停/单步时的边界。例如新增“等待一拍”，应明确它是一个不移动、不转向的原子动作；不要直接在解释器中写异步 `setTimeout`。
2. **扩展类型。** 在 `src/types/index.ts` 的 `InstructionType` 和 `Instruction` 联合类型中加入节点结构。参数应是明确的有限类型或有界数字，不能接受代码、HTML 或资源 URL。若需新的执行反馈字段，一并扩展 `ExecutionContext` 或 `RuntimeState`。
3. **扩展校验。** 在 `src/engine/validation.ts` 中更新类型白名单、准确字段集合、参数上下限、深度/节点计数及关卡限制。校验要覆盖未调用函数和循环内部。新容器还必须定义是否增加结构深度、如何检测递归与过深输入。错误信息应指向节点并使用孩子能理解的中文。
4. **实现解释器。** 在 `src/engine/interpreter.ts` 中增加明确的分支和原子状态更新。现有动作分支不能把新的节点误当作转向。保持 `step()` 至多一个原子动作、控制结构惰性推进、统一预算及正常结束判断。若新动作改变地图，应使用运行副本，不能修改 `Level`。
5. **扩展积木数据操作。** 更新 `src/features/editor/tree.ts` 的默认参数构造。新容器需纳入 `locate`、`getNodes`、`updateNode`、`cloneInstruction`、`countNodes`、深度检测和循环/函数移动约束。普通原子节点应直接复用现有 ID、复制和排序规则。
6. **设计可操作的积木。** 在 `ProgramEditor.tsx` 的名称表、`BlockIcon`、参数控件和积木库中加入图标与简短中文，并在 `editor.css` 中添加符合设计系统的颜色。数字参数应附着在该积木上。同步支持点击、鼠标、触屏拖动和键盘操作，提供可读的无障碍名称。
7. **处理展示。** 如果需要新 SVG 展示或声音，仅修改对应视图/声音模块；同步更新 `ExecutionBreadcrumb.tsx` 中的指令显示名称。展示接收解释器结果，不能另外计算一套移动规则。需要特别处理减少动画时的辨识度。新增延时效果应通过播放器展示间隔实现，不能让旧异步回调绕过代数取消标记。
8. **开放课程与备份兼容性。** 只在适合的 `Level.allowed` 中开放新指令，并增加示范关卡/参考解。当前导入只支持版本 1 和当前明确白名单；如果变更文件格式或已有节点含义，应同时升级 `ProgramFile`、导入导出版本判断及迁移测试。不要让旧版文件静默获得新语义。本地存档 `SaveData.version` 只有在存档格式变化时才升级并实现相应迁移。
9. **补足测试。** 增加合法/非法参数、执行结果、原子动作数量、预算消耗、单步、暂停继续、重置取消、嵌套循环/函数中的反馈、导入导出往返以及未开放关卡拒绝等测试。新指令涉及页面输入时，还需实际运行浏览器交互测试。

`src/engine/player.ts` 通常不需要知道新增指令名称；它只调度解释器步骤。若必须改播放器，应说明为什么现有原子动作抽象不足，并保留全部暂停、速度、取消和并发防护测试。

## 维护时保持的约束

执行与排序依赖数据树，不读 DOM 几何来推断程序顺序。未知导入字段一律拒绝。任何参数扩展都要同时调整校验、编辑控件及测试，不能只修改 UI 上限。参考解始终经同一解释器验证。保存允许未完成的构思，运行必须重新严格校验。

新增依赖时按实际安装版本查阅官方 API，固定精确版本并更新 `package-lock.json`。不得混用旧版 `@dnd-kit/core` 的 API 与当前 `@dnd-kit/react`/`@dnd-kit/dom` 0.5.0 写法。使用 Node.js 22.12 或以上版本；开发、测试与构建命令以根目录 `package.json` 为准。
